# Codex App Server local (prepared, off)

`app/codex_app_server.py` is an optional stdio JSONL client for the official Codex App Server. It is not connected to the main conversation or to `cloud-worker/`. Importing the module opens no process, socket, account, microphone, or memory store. Defaults are `enabled=false` and `turns_enabled=false`.

## Current state

- The environment tests use only `FakeRpc` and synthetic text. They test handshake, per-project thread mapping, event streaming, cancellation, explicit-send gating, lost-ack uncertainty, and restart recovery. They do not run Codex, sign in, or perform inference.
- The implementation does not sign in or start inference. An actual connection remains disabled until its account and tool isolation have been verified.
- No API key, OAuth grant, MCP server, provider, or remote listener is configured. The service is explicitly local only; do not expose App Server over WebSocket or host it in Sites/Worker.
- The App Server process uses an explicitly selected executable path and sets `HOME` and `CODEX_HOME` to a dedicated profile. This separates `config.toml`, local plugins/skills and file-backed `auth.json` from the global profile, but it does not by itself guarantee credential isolation: Codex may use the OS keyring. The official auth docs list `file`, `keyring`, `auto` and `ephemeral` storage; with keyring, the credential store is OS-wide. No profile is created and no login flow is started by this patch.
- Each exact project ID maps to one persistent App Server thread and the canonical configured project root. Changing a project's root blocks resumption until the old mapping is manually resolved. Cerebro does not prepend or read project-memory records; only the text passed by the caller is sent.
- A private local ledger fsyncs the operation ID and prompt hash before a turn request. A timeout, lost acknowledgement, restart, or unknown outcome stays unresolved and blocks further sends for that project. There is no automatic retry. Inspect App Server history before any manual resolution.
- Requests use the official `thread/start` / `thread/resume`, `turn/start`, `thread/turns/list`, and `turn/interrupt` methods over stdio JSONL. The requested sandbox is read-only with read access limited to the configured project root. Command, file-change, filesystem/network permission, and MCP approval requests are denied; unknown server requests fail closed.
- A new App Server thread is persistent by default. The official documentation describes `ephemeral: true` for `thread/fork`, not for `thread/start`; that requires an existing thread and cannot make the first test in-memory-only. Any later real turn may therefore create a local thread record.
- The code does not yet provide an approval UI or a verified policy that prevents every built-in tool from running under every App Server configuration. Real turns stay disabled until that is resolved. It does not execute commands or publish changes itself.
- The process launcher adds per-process overrides for shell execution, plugins, MCP, app tools, web search, and transcript auto-history. These are prepared values only; they have not been validated against every App Server version or tested for precedence over managed settings. `--ignore-user-config` is documented for `codex exec`, not App Server, so this integration does not use it. `features.plugins=false` is not a universal override for managed plugin state, and `apps._default.enabled=false` may have per-app overrides. A clean `CODEX_HOME` separates file-backed settings; it does not guarantee isolation from the operating-system credential store. Copying tokens or changing global config is out of scope.

## Enabling is not a one-step switch

Before enabling a test turn, verify a fresh profile with no user `config.toml`, MCP servers, plugins, hooks, skills, notification commands, or workspace project overrides; use a temporary empty working directory; disable command execution and use a read-only sandbox; and confirm no app/MCP/plugin tools are active. A separate `CODEX_HOME` isolates on-disk settings, but OS-keyring reuse and managed defaults must also be checked. The official auth reference defines `cli_auth_credentials_store="ephemeral"` as process-memory-only. A fresh official sign-in with ephemeral storage can isolate the auth store from a previously cached file/keyring login; obtain explicit authorization before starting that separate login flow. If a supported setup cannot prove zero active tools, keep the turn disabled.

This App Server path is not a cloud adapter. OpenAI's [official App Server documentation](https://learn.chatgpt.com/docs/app-server) describes local `stdio://` JSONL and identifies WebSocket as experimental and unsupported for production. The same docs state App Server auth has never been permitted for hosted services. The CLI reference documents `--ignore-user-config` only for `codex exec`; it is not a safe substitute for App Server. The App Server reference shows `thread/start` as a persistent thread by default and documents `ephemeral: true` only on `thread/fork`. Official [authentication guidance](https://learn.chatgpt.com/docs/auth) says file-backed auth lives under `CODEX_HOME`, keyring auth uses the OS credential store, and ephemeral auth lasts only for a process. The only known alternative that isolates account storage is a separate official App Server login using ephemeral credentials, which requires explicit approval for that login flow; without it, leave this feature disabled.

## Local model compatibility

The adapter is separate from the local-model runtime and does not replace project history, chat, speech, or recovery. It is not connected to Jarvis conversation; the capability catalog reports its disabled state. Synthetic transport tests do not establish a real connection or inference.


## Compatibility checkpoint: installed macOS CLI 0.163.0-alpha.10.2

The Mac installation replaces the simulated `onRequest` policy with a granular policy rejecting all five approval/escalation categories. It uses a named filesystem permission profile (minimal runtime reads plus the exact project root, no command network), rather than the unsupported `sandboxPolicy.access` object. `thread/start` defines the profile; `turn/start` selects it. Filesystem behavior was verified using the official CLI sandbox with managed requirements: inside read allowed; outside read, write and symlink escape denied. This does not verify App Server startup or inference. The adapter remains disabled and real turns remain disabled. Runtime state/log writes and effective App Server capabilities still require verification before connection. No new authentication is performed.

The macOS test fixtures resolve temporary paths before comparing roots, preserving canonical project isolation across `/var` and `/private/var` aliases. All 89 Python tests and three Node suites passed on this Mac; transport tests remain synthetic.
