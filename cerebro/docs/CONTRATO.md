# Contrato de datos, versión 1

La exportación JSON usa la raíz `{schemaVersion, config, events, transcripts, actions, messages}`. `messages` es opcional para aceptar archivos anteriores de versión 1; el almacén actual la exporta siempre. `schemaVersion` debe ser `1`; el importador valida cada propiedad, IDs, fechas ISO 8601 con zona, proyectos y transiciones antes de escribir. `config` contiene `{timezone, source, schedule, executionNote}`. Cada franja usa `{startDate,time,label,windowHours,flexible}`; windowHours admite null cuando la duración no está acreditada.

`events` conserva el historial completo: `{id,at,op,entity,evidence}`. La entidad es `{id,kind,projectId,title,body,status,priority,nextAction}`. `kind` puede ser project, instruction, decision, task, checkpoint o blocker; source conserva una fuente inmutable. `op` es create/update; instruction, decision, checkpoint y source son inmutables. Las instrucciones y fuentes globales pueden tener projectId vacío. Los estados son pendiente, en curso, bloqueado, preparado, probado, publicado y completado. La etiqueta adicional sin verificar conserva estados históricos sin afirmar verificación actual. Evidencias llevan enlaces o referencias `transcript:<id>`. Tareas derivadas validan que exista primero el fragmento.

`transcripts` preserva `{id,at,original,source,speaker,order,persistence}`. La app asigna `order` y `persistence=persistido` después del `fsync` del registro local. Mismo ID y mismo contenido es idempotente. Mismo ID con contenido distinto es conflicto. La interfaz conserva el ID pendiente en almacenamiento local del navegador, aislado por proyecto, para que un reintento explícito conserve la identidad; al volver, consulta el almacén antes de reenviar. ID distinto preserva una repetición textual legítima. Los originales no se editan ni resumen.

`messages` guarda mensajes de texto recibidos como `{id,at,projectId,role,text,channel,persistence}`. `role` es `user`, `channel` es `text` y `persistence` es `persistido`. El ID debe ser único y `projectId` debe nombrar un proyecto existente. Son append-only, se exportan con el JSON y el Markdown, y se muestran solo en la memoria de ese proyecto. Reintentar el mismo ID y contenido es idempotente, incluso después de un reinicio; reutilizarlo con otro contenido causa conflicto. La interfaz conserva localmente el ID/texto del intento para reintentar tras fallo; después de recargar comprueba el estado del servidor y no retransmite si el ID ya existe. Un nuevo envío intencional recibe otro ID aunque el texto coincida. No se generan respuestas de asistente; guardar mensajes no invoca motores de voz. Jarvis puede leer aparte una selección explícita con TTS del navegador, pero no persiste audio ni crea un registro de transcripción.

`actions` es un historial de estados de cola. Cada versión registra `{id,at,actionId,type,state,outcome,intent,checkpoint,dependsOn,idempotencyKey,title,projectId,evidence}`. Tipos task/code/external_send; estados pending/in_progress/blocked/uncertain/completed; outcomes not_started/unknown/succeeded/failed. La intención y dependencias se registran al crear la tarea y son inmutables. Para señalar trabajo reanudable se escoge la tarea pendiente más antigua cuyas dependencias estén completadas; una tarea bloqueada o incierta no detiene tareas independientes. Un resultado incierto requiere comprobación humana y evidencia antes de resolverlo. No existe reintento automático. Completar requiere `succeeded` y evidencia. El ledger conserva estados anteriores y no invoca efectos externos. Un reenvío exacto del mismo `actionId` e intención devuelve la entrada ya persistida antes de comprobar la revisión de la solicitud; cambios de estado continúan sujetos a revisión y validación normales. La interfaz conserva el borrador/IDs de intento en `localStorage`, con clave por proyecto, y verifica el ID después de recargar antes de ofrecer el reintento.

El importador añade IDs nuevos, es idempotente y valida el resultado combinado antes de escribir. Una modificación sobre una versión ya conocida crea conflicto, nunca sobrescritura silenciosa. Markdown contiene la narrativa legible y un bloque canónico codificado que permite round-trip exacto del JSON; no debe eliminarse ese bloque si se quiere reimportar.

El intercambio local `sync_local.py` compara almacenes en disco con servidores detenidos. Primero simula ambas fusiones; conflictos bloquean ambas escrituras. Sincroniza el ledger, nunca reejecuta acciones. Guarda `sync.json` con fecha/peer/IDs reconocidos y muestra IDs en outbox. Es un protocolo para rutas locales compartidas o medios que el usuario transporte, no sincronización automática en internet.

## API local para Jarvis

La vista Jarvis usa el mismo proceso de Cerebro y no carga el documento JSON completo para construir la red:

- `GET /api/projects` devuelve `{count, projects}` con únicamente `id`, `title`, `status`, `priority` y `nextAction` de los proyectos existentes.
- `GET /api/projects/{projectId}/memory?q=&type=&limit=` devuelve `{projectId, query, type, total, limit, hasMore, records}` y filtra todo el historial por el ID exacto del proyecto. Los tipos válidos son `all`, los tipos de entidad y `action`, `message` o `transcript`.
- `GET /api/session` devuelve `{token}` para operaciones locales de esta sesión; el token es efímero y no es una credencial de proveedor.
- `POST /api/messages` acepta exactamente `{id, projectId, text}` en JSON y requiere el token en `X-Cerebro-Token` y un origen local autorizado. La operación anexa un mensaje `role=user`, `channel=text`, `persistence=persistido` al diario. El mismo ID y contenido son idempotentes; el mismo ID con otro contenido es un conflicto. El usuario inicia el envío explícitamente. La interfaz registra localmente el intento antes de enviar, verifica por ID tras reiniciar y no reintenta en segundo plano.

Los endpoints funcionan solo contra el servidor local de loopback, aplican validación y el límite global del almacén. Las respuestas no habilitan acceso desde la red ni crean sincronización web.
