# Homepage content administration

## Scope and access

The existing administrator identities and sign-in rules are unchanged. `/admin#contenido` manages the homepage hero text, its two existing button labels (destinations stay fixed), the Mi Finca introduction, the hero photograph/alt text, and the homepage title/description used in search and social metadata. Other website sections, navigation/branding, articles, moderation, maps and existing workflows remain outside this slice.

1. Edit the fields and optionally upload a photograph you have permission to publish.
2. **Guardar borrador** persists the complete draft in D1 without changing the public page.
3. **Vista previa guardada** opens `/admin/home-preview`, using the actual homepage renderer. It requires the existing administrator session and is excluded from indexing and HTTP caching.
4. **Publicar inicio** requires a saved draft and an explicit confirmation. Publication atomically copies the saved draft into the public snapshot. Unsaved local edits cannot accidentally be published.

Multiple administrators/tabs are protected by a UUID revision compare-and-swap on both save and publish. A conflict preserves local text and asks the editor to copy changes before explicitly reloading. Closing the page with unsaved changes invokes the browser's standard warning. If a response is lost after a write, reload to determine the authoritative revision rather than overwriting it.

## Storage and rollout

- Additive migration: `drizzle/0008_wild_sinister_six.sql`, generated with `npm run db:generate`; matching snapshot and journal entry are included.
- New table: `website_content` (`id`, `draft_json`, `published_json`, `revision`, `updated_at`, `published_at`). No seed, backfill, deletion, or changes to existing tables.
- Existing `DB` and `BUCKET` bindings are reused. No credentials, roles, new service, paid image API, or hosting configuration changes.
- No remote migration or deployment was performed. The site owner should review the migration and publish through the normal Sites pipeline.
- A fresh/missing/malformed public record or temporary database outage falls back to the previous hardcoded homepage content. The admin API reports storage failures instead of pretending a save succeeded.
- Images are reduced to a maximum 1920-pixel edge and encoded in the browser, then server-validated by MIME signature, byte count and dimensions. R2 keys are generated by the server under `website/home/<uuid>.<extension>`.
- An unreferenced or draft image is accessible only to existing administrators. The public media endpoint exposes only the photograph in the currently published snapshot. Replacing it removes anonymous access to the previous photograph. Removed/unreferenced objects are retained in R2; automatic deletion and a media library are outside this slice.
- CMS-uploaded photographs are online resources and are not added to the existing downloadable offline asset manifest. Offline text uses the last downloaded homepage snapshot; the original bundled photograph remains in the offline pack. Extending offline downloads to CMS media is outside this slice.
- To restore the original photo, use **Usar imagen original**, save and publish. Text can be edited back to the desired previous values. Version history/one-click rollback is not included.

## Validation

`node --test tests/home-content-admin.test.mjs` executes the real endpoints and SQL against in-memory SQLite with a D1 adapter and a synthetic R2 bucket. It covers denied anonymous/non-admin access, cross-site mutations, strict body/schema validation, public defaults, draft isolation, publication, save/publish races, unavailable storage, image validation/privacy, and missing-image refusal. Existing homepage regression tests now follow the extracted shared renderer. `tsc --noEmit` and the production build also validate this slice. The full existing suite plus the CMS tests passes: 1,168 tests. The public homepage explicitly revalidates while remaining cache-eligible for the existing downloaded offline library; private previews stay no-store.

Live authentication/R2/D1 and visual browser checks are still required in a supported private preview before production rollout. No browser workaround or production content mutation was used for local testing.
